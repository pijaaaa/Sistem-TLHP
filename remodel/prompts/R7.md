# R7 — Review SPI & Siklus Revisi per Action Plan

## Konteks
R0–R6 selesai. Admin SPI meninjau action plan yang `DIAJUKAN_KE_SPI` dalam **satu halaman**, menilai tiap tindak lanjut Sesuai/Revisi. Revisi dilakukan **per action plan**: Awal → Revisi 1, 2, … Baca roadmap bagian 4–5.

## Tugas
**Backend**
1. Tabel `spi_reviews` (action_plan_id, revision_no, reviewer_id, completed_at) dan `spi_review_items` (spi_review_id, follow_up_id, result `SESUAI`|`REVISI`, note).
2. Tabel `action_plan_revisions`: action_plan_id, revision_no, requested_by, requested_role, source (`SPI_REVIEW`|`EXTERNAL_STATUS`), reason, requested_at, forwarded_to_pic_at, new_deadline (nullable).
3. `SpiReviewService` (hanya `admin_spi`):
   - `assess(actionPlan, items[])` simpan penilaian per TL (catatan **wajib** untuk `REVISI`); dapat disimpan bertahap.
   - `complete(actionPlan)` ("Simpan & Selesaikan"): wajib semua TL revisi berjalan (aktif, status SELESAI) sudah dinilai. Ada ≥1 `REVISI` → AP `REVISI_SPI`, `current_revision + 1`, buat `action_plan_revisions` (siapa, kapan, alasan gabungan, opsional `new_deadline`). Semua `SESUAI` → AP `SESUAI` (dibekukan). Selalu panggil `FindingStatusService::recompute`. Event `SpiReviewCompleted`.
4. `RevisionService::forwardToPic(actionPlan)` oleh `manager_dept`: AP `REVISI_SPI` → `PROSES_TINDAK_LANJUT`, set `forwarded_to_pic_at` (dan terapkan `new_deadline` bila ada). Event `RevisionForwarded`. PIC lalu menyusun TL **baru** (R4) pada revisi baru: `follow_ups.revision_no` = revisi berjalan, boleh `linked_follow_up_id` ke TL lama yang diperbaiki; deadline dan bobot baru (total revisi baru ≤ 100, wajib 100 saat ajukan ke SPI).
5. **TL lama tidak dihapus**: tetap tersimpan (deadline, progres, dokumen, diskusi, catatan SPI) sebagai riwayat read-only; progres AP hanya dari revisi berjalan.
6. **Pembekuan**: AP `SESUAI`/`CLOSED` read-only (service menolak perubahan TL/bobot/PIC). Hanya AP yang direvisi yang berjalan lagi.
7. Endpoint `GET /action-plans/{id}/review-bundle`: semua data untuk halaman Review SPI (info AP, riwayat revisi, TL revisi berjalan + riwayat laporan progres + dokumen + keputusan manager + komentar IA + diskusi). Di-cache pendek, query efisien (eager load, tanpa N+1).
8. Label revisi: `Awal`, `Revisi 1`, `Revisi 2`, … (helper/accessor).
9. Test: catatan wajib, complete ditolak bila ada TL belum dinilai, revisi menaikkan nomor & mencatat peminta, forward ke PIC, TL lama read-only dan tetap tersimpan, AP SESUAI beku, status temuan ter-recompute, hanya admin_spi.

**Frontend** (menu `spi_review`: `/review-spi`, `/review-spi/:actionPlanId`)
10. Daftar antrian AP `DIAJUKAN_KE_SPI`.
11. **Halaman Review SPI satu halaman**: panel info AP, `RevisionTabs` (Awal, Revisi 1, … read-only untuk riwayat), daftar TL dengan progres, dokumen (unduh satu per satu), keputusan manager, komentar IA, diskusi; pada tiap TL kontrol Sesuai/Revisi + catatan; tombol **Simpan & Selesaikan**.
12. Di sisi manager: AP `REVISI_SPI` menampilkan alasan revisi & tombol **Teruskan ke PIC**; di sisi PIC, tombol susun TL baru dengan opsi menautkan TL lama.

## Acceptance criteria
- Review SPI dapat dikerjakan sepenuhnya dalam satu halaman.
- Revisi hanya mengaktifkan kembali AP yang direvisi; AP Sesuai tidak bisa diubah.
- Riwayat revisi lengkap dan terbaca.

## Larangan
Jangan hapus TL/laporan/dokumen revisi lama. Jangan reset umur temuan. Jangan buat status eksternal (R8).
