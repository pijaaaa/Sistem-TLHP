# M2 — Data Master (Departemen & Karyawan) + Manajemen Akses

## Konteks
M0–M1 selesai. Departemen dan karyawan adalah data master. Menu dan izin dasar sudah ada. M2 fokus pada CRUD master data + UI manajemen akses.

## Tugas

### Backend

#### Departemen
1. Migration `departments` (jika belum lengkap dari M1): `id`, `code` (unik), `name`, `is_active`, `deleted_at` (soft delete), timestamps. Index pada `code` & `is_active`.
2. `DepartmentSeeder` — seed 13 departemen:

   | Kode        | Nama                     |
   |-------------|--------------------------|
   | FINANCE_ICT | FINANCE & ICT            |
   | EKS         | EKS                      |
   | EPT         | EPT                      |
   | PRODUCTION  | PRODUCTION OPERATION     |
   | DWO         | DWO                      |
   | QHSE        | QHSE                     |
   | HCM         | HCM                      |
   | SCM         | SCM                      |
   | OPS_SUPPORT | OPERATION SUPPORT        |
   | CORSEC      | CORSEC                   |
   | EA          | EA                       |
   | SPRM        | SPRM                     |
   | IA          | IA                       |

   (**EGILUY tidak dimasukkan** — pastikan tidak ada di seed.)
3. API Resource `DepartmentResource`, FormRequest validasi, Policy `DepartmentPolicy`.
4. Endpoint CRUD (`index`, `show`, `store`, `update`, `destroy` soft-delete), pagination, pencarian `name`/`code`, filter `is_active`.
5. Cache: `departments.active.all` (untuk dropdown) via `CacheService`. Invalidasi otomatis saat create/update/delete/soft-delete.

#### Karyawan (employees)
6. Migration `employees`: `id`, `nip` (unik), `name`, `email`, `phone` (nullable), `department_id` (FK → departments), `position` (enum: `manager`, `staff`), `is_active`, soft delete, timestamps. Index gabungan `department_id`+`position`.
7. Aturan bisnis: **maksimal 1 `manager` aktif per departemen**. Validasi di FormRequest & Service (error: *"Departemen {name} sudah memiliki manager aktif."*). Manager departemen IA = role `manager_ia` (dicatat via `users.role`), bukan field position — position tetap `manager`.
8. `EmployeeUser` — relasi `users.employee_id` 1:1. Satu karyawan = satu akun = satu departemen = satu jabatan.
   - Role user: diturunkan otomatis dari kombinasi departemen + position, dengan aturan:
     - `manager` di departemen SPI → `manager_spi`
     - `manager` di departemen IA → `manager_ia`
     - `manager` di departemen lain → `manager_dept`
     - `staff` di departemen IA → `manager_ia` (per roadmap: Manager IA bertindak sebagai Manager Dept)
     - `staff` di departemen SPI → `admin_spi`
     - `staff` di departemen lain → `staff_dept`
   - **Exception / override**: admin perlu pabilih role di dropdown terbatas (hanya role yang sah untuk kombinasi dept+position). Jelaskan logikanya di ringkasan agis.
   - `username`: auto-generate dari `nip`/`email`.
   - `password` awal: generate acak, dikirim via reset link (gunakan `password.reset` bawaan Laravel) — tidak ditampilkan di UI.
9. CRUD API `employees` mirip departemen; saat create otomatis membuat akun user dalam transaksi. Soft-delete & restore mengembalikan user is_active false/true.
10. Endpoint `POST /employees/{id}/reset-password` → generate token reset password.
11. Lookup ringan untuk dropdown (semua role bisa akses): `/lookups/departments`, `/lookups/employees?department_id=`. Response ringan (hanya id, name, code/nip). Cache `CacheService` untuk list aktif; invalidasi otomatis.

#### Manajemen Akses (menu `access.permissions`)
12. API (hanya superadmin / role dengan izin menu `access.permissions`):
    - `GET /access/menus` — daftar semua menu (nama, urutan, is_active, kode, path — kode/path readonly).
    - `PUT /access/menus/{id}` — update `name`, `sort_order`, `is_active`; validasi kode/path tidak berubah.
    - `GET /access/roles/{role}/permissions` — matriks izin role vs menu.
    - `PUT /access/roles/{role}/permissions` — simpan matriks; validasi `can_view` menjadi true bila ada create/update/delete true.
    - `GET /access/users/{user}/permissions` — izin user (override) + izin role dasar.
    - `PUT /access/users/{user}/permissions` — set override (boleh null = kembali ke role); validasi sama.
    - `POST /access/users/{user}/reset-overrides` — reset semua override ke null → kembali pakai role.
13. Proteksi: superadmin selalu penuh & bisa reset sendiri; tidak bisa mengunci akses ke `access.permissions` secara sengaja (gunakan `firstOrNew` / bypass validasi superadmin di PermissionService).
14. Audit trail: setiap perubahan izin — role/user, menu, action, old_value, new_value — dicatat via `audit()` helper dari M0.
15. Cache: `PermissionService::invalidateForUser($user)` & `invalidateForRole($role)` panggil otomatis saat izin berubah; notifikasi semua user terdampak.
16. Test: perubahan izin langsung efektif di `/auth/me`; proteksi lockout tak bisa mencapai superadmin; user non-berhak (403).

### Frontend
17. Halaman **Departemen** & **Karyawan** pakai DataTable, Modal, FormField reusable (dari M0). Buat hook generik `useCrudResource(endpoint)` → `{data, loading, reload, create, update, remove}` agar tidak duplikasi markup.
18. Komponen reusable:
    - `<DepartmentSelect />` — ambil dari cache `CacheService` via lookup endpoint, `staleTime` panjang.
    - `<EmployeeSelect departmentId? />` — serupa, filter per departemen.
    Dipakai semua milestone berikutnya.
19. Halaman **Manajemen Akses** (`access.permissions`):
    - Tab **"Per Role"**: tabel matrix — baris menu, kolom view/create/update/delete, `PermissionMatrix` reusable, save sekali klik.
    - Tab **"Per Karyawan"**: `EmployeeSelect`, tampilkan izin efektif (warna/penanda override), ubah, reset ke role.
    - Semua berbasis komponen reusable + hook TanStack Query; tidak hard-code departemen/user di FE.
20. DataTable & PageHeader (dari M0) sudah otomatis bersembunyi tombol aksi tidak punya izin — tambahkan prop `permissionMenu` jika belum.

## Acceptance Criteria
- Dari UI, admin bisa buat karyawan `staff` departemen FINANCE & ICT hanya bisa `view` satu halaman & langsung terlihat setelah reload `/auth/me`.
- 13 departemen ter-seed; **EGILUY tidak ada**.
- Tidak bisa dua manager aktif di satu departemen; error jelas.
- Request ke `/lookups/departments` kedua kali tidak query DB (buktikan lewat test / log query).
- CRUD Departemen/Karyawan jalan dari UI.
- Kode halaman tidak menduplikasi markup (pakai hook generik + komponen reusable).

## Larangan
- Jangan hard-code daftar departemen di FE (wajib dari API).
- Jangan hapus fisik data master yang dipakai relasi.
- Jangan buat modul temuan (itu M3).
- Jangan izinkan edit kode menu/path dari UI — hanya nama, urutan, aktif.
- Jangan beri user biasa akses penuh ke akses permissions tanpa override eksplisit.

## Konvensi kode
- Ikuti `docs/roadmap.md`; semua rule M1 masih berlaku.
- Backend: Service → Policy → Resource; migration punya FK+index+softdelete.
- Cache pake `CacheService` eksplisit, invalidasi otomatis.
- FE: reusable komponen di `src/components/ui` + `src/components/shared`; hook di `src/hooks`.
- Bahasa UI Indonesia; variabel/tabel Inggris.
